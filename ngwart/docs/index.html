§ 1

Getting started

Install everything a bench station needs, then run the bundled demo against simulated instruments — no hardware required. 

# everything: UI, instrument backends, test suite
py -m pip install -r requirements.txt

# headless engine only (CI, program linting)
py -m pip install -r requirements-min.txt
py run.py ui programs/demo.yaml --simulate    # operator station
py run.py run programs/demo.yaml --simulate   # headless run
py run.py check TestTables/cargo.ods          # lint a legacy table
py -m pytest tests -q                         # 92 passed
Existing tables keep working

Every verb a v1 .ods table uses resolves unchanged. Point check at one before anything else — it reports what the table gets wrong without energising the fixture.

§ 2

How a program works

A program is a flat list of rows, read top to bottom. That shape is deliberate: a test engineer follows a sequence, and nesting would not help. Rows are grouped into sections.

SectionWhen it runsWhat belongs in it
<Modules>load time alias → driver, e.g. Camera → BaluffManager
<Vars>load time friendly name → l,c,p coordinate (new in v2)
<Config>once, before the test open ports and instruments, lay out the result grids
<Exec>the test itself every measurement and judgement
<Ehandling>only when jumped to the error-handler labels
<Teardown>always de-energise supplies, open relays (new in v2)

Control flow is labels and jumps. Execution begins after <Exec> and ends when the pointer runs past the last executable row — normally because the program jumped to a terminal label.

Why Ehandling sits after Exec

Real v1 tables close <Exec/> and then declare their handlers. Those labels are jump targets, so the executable range extends past the closing marker — you can jump into the block, but never fall into it.

§ 3

Anatomy of a row

Ten columns, unchanged from v1. The first two say what to do, the middle five are arguments, and the last three are the row's contract with the engine.

One row from the cargo fixture: close a relay on the second supply channel.
C0C1C2C3C4 C5C6C7C8C9
Serial EXCHANGEBYTES_LVS D2 48,49,43,47,47 48,49,43,47,47 5,5 — SERIAL_EX 1 CH1 + ON → UUT 2
module verb arguments on error alive comment

Module is an alias declared in <Modules>, so a table chooses its own drivers — swap BaluffManager for CameraManager and the rest of the program is untouched. On error names a label to jump to if the verb fails; leave it blank and failures route to STD_EX. Alive decides which units the row applies to.

§ 4

The alive mask

One fixture holds several boards. When a board fails, it is killed and every later row that names it is skipped — while the others carry on and get their own verdict. This is the mechanism that makes a multi-up fixture worth building.

Column 8Meaning
- or blankrun unconditionally
0,2run if UUT 0 or 2 is still alive
-,0,2run only if 0 and 2 are both alive

A unit is killed by a limit failure, by AKILL, or by VALIDATE_DET when the fixture reports it absent. The engine emits the mask on every change, so the UI dims a dead unit immediately.

§ 5

Named variables

Values live in a three-dimensional store addressed as line,column,page. v1 wrote those coordinates literally, which is how a product file ends up full of *0,1,2 and 39,0,29. Declare names instead: 

vars:
  uut0.vbat:   '2,0,0'
  uut0.iload:  '3,0,0'
  img.raw:     '4,0,0'

Then *uut0.vbat works anywhere *2,0,0 did. Both go through the same accessor, so a table can be migrated one line at a time and a half-converted file still runs. A leading * is accepted on destinations too, so there is no source/destination trap.

Errors name what you meant

Mistype a variable and the message lists the declared names and suggests the closest one — rather than an IndexError from inside the store.

§ 6

Errors and routing

When a verb fails, the engine looks at the row's on error column and jumps to that label. A blank column routes to STD_EX, which is what most rows in a real table rely on. 

ehandling:
  - [Flow, LABEL, SERIAL_EX, 'SERIAL FAILURE', '', '#E5484D']
  - [Flow, J, SHUTDOWN_ALL]
  - [Flow, LABEL, STD_EX, 'SYSTEM FAILURE', '', '#E5484D']
  - [Flow, J, SHUTDOWN_ALL]

Failures are not all the same, and the type decides what happens:

TypeMeansRoutable
ValidationFailurea measurement fell outside limits — a real rejectyes
HardwareErroran instrument misbehaved or is absent — the rig is at fault, not the boardyes
VerbErrorthe verb could not do its jobyes
ProgramErrorthe program itself is wrong — bad reference, unknown verbnever

A ProgramError is deliberately not routable. A broken program must stop rather than limp along on its own error handlers, and the distinction also keeps yield reporting honest: a board that fails a limit is a reject, a rig fault is not.

§ 7

Teardown

<Teardown> runs in a finally. It executes when the test passes, when it fails, when the operator presses stop, and when the engine hits an internal error. 

teardown:
  - [VISA, WRITE, DP2A243200206, 'OUTP OFF']
  - [VISA, WRITE, DP2A243200206, 'VOLT 0']
  - [Serial, EXCHANGEBYTES_LVS, D1, '111,102,102,47,47', '111,102,102,47,47', '5,5']
A teardown step that fails does not stop the rest

Failures inside teardown are logged and recorded, never re-raised — one stuck relay must not prevent the supply being switched off. This is the one place in the engine where an error is deliberately swallowed.

A program without a teardown block loads and runs, but validation warns about it. Add one.

§ 8

Validation

Because every verb declares its parameters, a whole program can be checked before the fixture is powered. This is the single biggest change from v1, where a mistyped verb surfaced as an AttributeError partway through a run with the supply already at 13.5 V.

Checked up front:

  • every module alias resolves to a registered driver
  • every verb exists — with a spelling suggestion when it does not
  • required arguments are present; unexpected ones are flagged
  • every jump target and error label exists
  • alive indices fit the initAlive count
  • data references fit the INITDATA dimensions
  • <ParallelTask> blocks are closed and not nested
  • no row has a verb but a blank module cell
$ py run.py check TestTables/cargo.ods

ERROR   row 124: 'VALIDATE_DET' has no module in column 0
        v1 raised KeyError here and diverted to the row's exception
        handler, so this step never actually ran.
ERROR   row 360: jump to undefined label 'Remove_DUT'
WARNING program: program has no <Teardown> section

8 error(s), 1 warning(s)

The operator UI runs the same check on load and refuses to arm Run until it is clean. Double-click a diagnostic to jump to the offending row.

§ 9

The serial matrix

v1 shipped 27 near-identical serial functions. Decoding the names shows they are one operation with four independent switches, so there is now one implementation and 27 aliases. Every old name still resolves.

operation

  • READ — receive only
  • EXCHANGE — write, then receive

payload

  • LINE — text
  • BYTES — comma-separated byte list

terminator

  • _LT_ — read to a newline
  • absent — read a fixed byte count

validation level

  • _LV0 store the response
  • _LV1 judge it
  • _LV2 judge, with retries
  • _LV3 judge, retry, kill the UUT
  • _LVS strict — retry, then raise

So EXCHANGEBYTES_LT_LV3 reads as write bytes, read a line, judge with retries, kill on failure. A fix to the retry logic now fixes every variant at once — which was emphatically not true before.

§ 10

Worked example

A two-unit program: wait for boards, power them, measure, judge, score, and always shut down. This is programs/demo.yaml, trimmed. 

modules:
  Flow: FlowManager
  Serial: WinSerialManager
  VISA: GlobalVISAManager
  Product: CargoManager

vars:
  det.raw:    '0,0,0'
  uut0.vbat:  '2,0,0'

config:
  - [TestData, initAlive, 2]
  - [Serial, FINDPORT, '115200,1', '066CFF383355...', CONTROL]
  - [Serial, OPEN, CONTROL]
  - [VISA, OPENALL, '10000']

exec:
  # poll until every board is seated
  - [Flow, LABEL, DETECTION, 'WAITING FOR BOARDS']
  - [Serial, EXCHANGELINE_LT_LV0, CONTROL, 'd/n', '', '', '*det.raw', SERIAL_EX]
  - [Flow, DELAY, '0.1']
  - [Flow, JNE, DETECTION, '*det.raw', '16']
  - [Product, VALIDATE_DET, '*det.raw']

  # energise
  - [VISA, WRITE, DP2A243200206, 'VOLT 13.5', '', '', '', VISA_EX]
  - [VISA, WRITE, DP2A243200206, 'OUTP ON', '', '', '', VISA_EX]
  - [Flow, DELAY, '0.2']

  # measure and judge: limits, destination, retries + which UUT
  - [VISA, MEASURE_FEVAL, DP2A243200206, 'MEAS:VOLT?',
     '13.0,14.0', '*uut0.vbat', '3,0,VBAT', VISA_EX]

  - [Product, VALIDATE]
  - [Flow, J, DONE]

teardown:
  - [VISA, WRITE, DP2A243200206, 'OUTP OFF']

§ 11

Debugging a failure

Written for the question "why did INTENSITY_A fail?" — which a log cannot answer and images can. The bundle holds the frame that was captured, the binary it was thresholded to, the contours that came out, and the search window the verb actually looked in. 

py run.py run TestTables/cargo.ods --debug   # ./debug/<name>_<stamp>/
FileContains
SUMMARY.txtthe verdict, and every failed point with its measured value and limits
images/the capture, the thresholded binary, and contours drawn with the search window marked
evalcont_row<N>_<TEST>.jsonthe window searched, what was found, and every contour near it
contours_row<N>.jsoncentroid and area of every contour
datastore.jsonevery populated cell, with its variable name
log.txt, run.jsonthe full log; every step with timing and outcome
environment.txtversions, and whether the vendor SDKs are present

In the UI, tick Debug bundle on the toolbar. Off by default: it writes images, so it costs disk and a little time per vision step.

§ 12

Simulation

--simulate swaps every backend for a model rather than a stub, which is what makes a dry run worth anything:

  • the supply tracks per-channel setpoints — measure with the output off and you read ~0, not a canned number
  • the control board reports boards absent, then present, so retry loops are genuinely exercised
  • relay boards echo their command frames, as the real Denkovi units do
  • the camera renders lit discs for the contour and LED verbs to find
Simulated runs are tagged

Reports carry <simulated>true</simulated>, so a dry run can never be mistaken downstream for a real one.

§ 13

Migrating from v1

These steps are a sequence — each one depends on the last.

  1. Lint the table. py run.py check table.ods. Fix what it reports; nothing else needs to change yet.
  2. Run it in simulation. py run.py run table.ods --simulate exercises the control flow without touching the fixture.
  3. Add a teardown block. The one thing a v1 table cannot express, and the reason a crashed run used to leave the supply on.
  4. Adopt any unported driver. A v1 manager works as-is: 
    from ngwart.drivers.legacy import adopt
adopt("CANManager", "/path/to/v1/src/CANManager.py")
    Each async def VERB(line, UI) becomes a verb, a shim stands in for the Tk UI, TestData globals are bound to the live context by reference, and "LABEL::msg" exceptions are translated back into typed errors.
  5. Convert to YAML when ready. py run.py convert table.ods program.yaml gives you a file that diffs in git — so a reviewer can see what changed between the revision that passed qualification and the one running now.

When the site driver should win

Some v1 drivers encode hardware knowledge a rewrite cannot re-derive. The Balluff camera is the clearest case: BaluffManager.py holds the mvIMPACT DeviceManager at module scope, because letting it be collected unloads the driver stack and turns every open handle into a dangling native pointer — the next call crashes the process rather than raising. It also carries the binning and AOI arithmetic, the packed-pixel buffer geometry, and the User1 white-balance parameter set. 

py run.py ui TestTables/cargo.ods --legacy ../cargobay/src

Only hardware drivers are replaced. UIManager, FlowManager and TestData stay on the v2 implementations — v1's UIManager writes to Tk widgets and would leave the Qt grids silently blank. Override with --legacy-only BaluffManager,WinSerialManager.

Adopted verbs are opaque to the validator

It can confirm a legacy verb exists, not that its arguments are sane. Port the ones you touch most often; leave the rest until they get in your way.

§ 14

Architecture

The engine never imports Qt, and the UI never touches the data store. That seam is the reason the display cannot freeze: no widget is touched from the thread doing serial I/O. 

ngwart/
  engine/          no UI imports, no vendor SDKs — runs headless
    registry.py    @verb with declared parameters → makes linting possible
    program.py     rows, sections, labels
    context.py     data store, alive mask, events
    sequencer.py   the run loop: jumps, parallel blocks, teardown
    validator.py   pre-flight checks
    errors.py      typed, routable exceptions
    loaders/       .ods (no pandas), .txt, .csv, .yaml
  drivers/
    backends/      sim + real behind one protocol
    legacy.py      adopt unported v1 managers as-is
  ui/              PySide6; bridge.py is the only Qt↔engine seam
  reports/         XML / JSON / CSV from the run record

The engine emits plain dataclass events to a listener. The Qt bridge is a QObject living on the GUI thread, so every signal it re-emits is delivered through the event queue and every slot runs on the GUI thread. Swap the listener for a recorder and the same run is a unit test.

What changed, and why

NGINE v1NGWART
Threading UI and test loop share one asyncio loop; 36 blocking serial calls inside async def, no executors engine on a worker thread, Qt on the main thread
<ParallelTask> gather over blocking calls — ran sequentially real thread pool
Errors Exception(label + "::" + msg), 129 times typed, route as a field, tracebacks preserved
Validationnonewhole program, before power-up
Teardownnoneguaranteed
Data refsdata[39][0][29]*uut1.vbat

Grid verbs24 copy-pasted functions1, registered per grid
